Reproducibility

How to rerun the analysis and where the results can mislead

Every number on this site is computed from synthetic data generated by R/simulate.R from seed 34, with every analysis choice set in params.yaml. Nothing is downloaded during a render, so rendering the same commit with the same package versions gives the same results. This page explains how to rebuild the site, records the environment it was built in, and states where the results can mislead.

Quick start

The code and data are in the GitHub repository patrick-lefler/three-questions-for-any-risk-model. To rebuild everything from a clean copy:

git clone https://github.com/patrick-lefler/three-questions-for-any-risk-model
cd three-questions-for-any-risk-model
Rscript -e 'renv::restore()'   # once: install the package versions pinned in renv.lock
Rscript run_all.R

The rendered site is written to docs/. run_all.R runs the scripts in the Pipeline table in order, stops at the first failure, clears the Quarto freeze cache, calls quarto render, then runs the word count and the page tests. To re-render the pages from the artifacts already in data/ without rerunning the analysis, run quarto render instead.

Pipeline

Script What it does Main outputs
R/simulate.R Generates the synthetic NorthPoint vendor-incident panel with three planted features (about 1.5% incident rate, confounding by vendor size, patch-latency drift after month 36) and checks them vendor_panel.csv/.parquet, vendors.csv, truth.rds
R/fit_models.R Trains the VendorScore black box (xgboost) and the bank’s own incident-association model; keeps scores only vendorscore.csv/.parquet, models.rds
R/check_packages.R Gate 0: checks probcal, forecastdom and falsifyr against the panel package_check.txt
R/analysis_calibration.R Page 2: calibration of the raw scores and the recalibration overlay calibration.rds
R/analysis_forecast.R Page 3: raw VendorScore against a 12-month rolling average forecast.rds
R/analysis_fragility.R Page 4: specification curve, deletion search and 40-seed sweep (about 2 minutes) fragility.rds, specification_manifest.csv, seed_sweep.csv, deletion_path.csv, falsifyr_attacks.csv
R/build_manifest.R Writes the audit artifacts analysis_manifest.csv, checksums.csv, session_info.txt
tests/run_tests.R Runs the simulation and artifact test suites test_results.csv

All outputs are written to data/. The scripts share R/params.R (reads params.yaml), R/windows.R (the analysis windows) and R/baseline.R (the bank’s baseline model). Each script reads the files written by the ones before it, so run them in this order. The pages source only R/common.R (palette, plot theme, formatters) and read the artifacts in data/; they never refit a model.

Data

All data are synthetic. R/simulate.R generates a panel of 300 vendors over 48 months from seed 34 (set through the SIM_SEED environment variable, default 34). The simulator’s own parameters live in that script and are listed under simulator in params.yaml for reference only. Every other file in data/ is written by the pipeline, so the whole folder can be regenerated from code in the repository. R/build_manifest.R records the checksums of the last pipeline run in data/checksums.csv.

The checksums below identify the exact files used in this render. A different checksum means a different file. The generator script and params.yaml are included because any edit to them changes the data.

How to read the table
Each row is one data file. The MD5 column is a checksum: a short fingerprint computed from the file’s exact contents, so changing even one character gives a completely different fingerprint.

What the table tells you
Anyone rerunning the analysis can compute the same checksums on their copies. If every fingerprint matches, they are working from identical inputs; a mismatch means a file differs, and any difference in results should be traced to that file first.

Parameters and seeds

Every analysis choice lives in params.yaml, which the scripts read. Each value is labelled as an assumption, a convention or a feature planted in the synthetic data, with a range over which a sensitivity check would be reasonable. The table shows the main ones.

How to read the table
Each row is a setting that shapes the results. The last column says whether it is an analyst’s assumption, a standard convention, or a feature planted in the synthetic data.

What the table tells you
Most settings are assumptions. Changing the windows, risk bands or deletion budget would change the reported numbers, so each is recorded in one place.

Every random stream is seeded explicitly. R/simulate.R calls set.seed() with the SIM_SEED value (default 34); R/fit_models.R, R/analysis_calibration.R and R/analysis_fragility.R each call set.seed(par_get("seed")) at the top. The xgboost model is trained with nthread = 1, and no step runs in parallel, so results do not depend on the number of cores. The seed sweep on page 4 reruns the generator with seeds 1 to 40 in temporary folders and never touches data/.

Tests

tests/run_tests.R runs two test suites before the site is rendered and records the results in data/test_results.csv:

Suite Script Checks passed Status
simulation tests/test_simulate.R 34 passed
artifacts tests/test_fit_models.R 72 passed

How to read the table
Each row is one test suite from the last pipeline run. “Simulation” checks that the generator plants the intended features and that the same seed gives the same panel; “artifacts” checks the fitted models, windows, baseline, benchmark and resampling.

What the table tells you
All 106 checks passed on the run that produced these results. If a rebuild reports fewer passes or a failure, the artifacts in data/ differ from those behind this site.

After rendering, tests/test_pages.R checks the rendered pages (no errors, word budget, figure and table limits, reader notes) and tests/check_links.R checks every internal and external link. These page checks are not recorded in the table.

Caching

  • Analysis artifacts (data/*.rds, data/*.csv). The pipeline scripts write them; the pages only read them. They are committed to git, so quarto render on a fresh clone works without rerunning the analysis. Nothing invalidates them automatically: after editing a script or params.yaml, run Rscript run_all.R to rebuild them.
  • Quarto freeze (_freeze/). _quarto.yml sets freeze: auto, so a full quarto render re-executes a page only when that page’s .qmd file changes. Edits to the R/ scripts or to the artifacts in data/ do not count as a change. run_all.R deletes _freeze/ before rendering for this reason. After changing anything else, render each page explicitly (for example quarto render index.qmd), because Quarto always executes a page that is rendered on its own. _freeze/ is not in git.

Known limitations

Limits of reproducibility

  • Bit-for-bit equality is expected only on the same platform and package versions. Floating-point and BLAS differences across machines can change low-order digits.
  • The three testing packages (probcal 0.2.0, forecastdom 0.1.0, falsifyr 1.0.0) are young CRAN releases whose defaults may change between versions; renv::restore() installs the pinned versions from the CRAN archive. The VendorScore scores depend on the xgboost version.
  • Quarto versions affect rendering, not the numbers.

Model limitations

  1. Synthetic data. Confounding, regime shift and overconfidence are planted. Real use needs NorthPoint’s vendor-month panel, incident definition and dated SOC 2 reports.
  2. Few events. 75 evaluation incidents and 18 forecast months limit power; more history could change pages 2 and 3.
  3. Thin overlay window. Six months and 28 incidents is little. A real overlay needs a refit schedule and tolerances set in advance.
  4. Information timing. Start-of-month availability of patch latency and financial health is assumed; real feeds need timestamps.
  5. One dataset. Seed 34 was chosen in development; the seed sweep on page 4 checks repeatability only.
  6. Partial validation. Scores and outcomes only; the vendor’s internals stay unseen.

The results show how the three questions can be put to a black-box score using only its outputs and the bank’s own outcomes. They are not evidence about any real vendor model. Treat the numbers as an illustration of the method, and rerun the analysis on real data before drawing conclusions about a specific model.
