# SPEC — Trust, but Verify: Validating a Vendor Risk Model You Can't See Inside

Project specification for a coding agent. Read this document fully before
writing any code.

## 0. What is being built

A four-page Quarto website forming one Seeking Eureka research series on
model risk. A fictional regional bank (NorthPoint Bank, ~$45B assets)
licenses a black-box third-party vendor-incident model called VendorScore.
The bank cannot see its code, training data, or methodology — it receives
only monthly risk scores. The series asks three questions about that model:

1. Are its probabilities honest? (calibration — CRAN package `probcal`)
2. Does it beat a simple model? (forecast dominance — `forecastdom`)
3. Would its headline finding survive a push? (fragility — `falsifyr`)

Regulatory anchor: the April 2026 interagency Supervisory Guidance on Model
Risk Management (Federal Reserve, FDIC, OCC), which revises the earlier
SR 11-7 guidance. The guidance is explicitly non-prescriptive, so all
recommendations use the phrase "sound practice suggests…", never
"regulators require…". Score-based testing provides PARTIAL validation only;
conceptual soundness of the proprietary model depends on what the vendor
discloses, and the pages must say so.

**Hard constraints (non-negotiable):**
- 4 Quarto pages, total prose ≤ 3,750 words (hard ceiling 4,000).
- Per page: at most 3 figures and 1 table. Code folded by default.
- One shared synthetic dataset drives all pages.
- All results reproducible from a fixed seed (34).
- The case study is a bank (the guidance targets banks >$30B in assets).
  Page 1 notes in one sentence that asset managers and fintechs can adopt
  the same practices voluntarily.

**Already complete and validated — do not redesign:**
- `R/simulate.R` — generates the panel; 34/34 tests pass.
- `tests/test_simulate.R` — test suite for the simulation.
- Default seed 34 chosen from seeds 1–40 (checks pass on 26 of 40 seeds).

## 2. The data (already built — contracts only)

`data/vendor_panel.csv` — 14,400 rows (300 vendors × 48 months, Jan 2022–Dec 2025).

Columns (exact, in order):
`vendor_id, month, date, tier, data_access, soc2_current, vendor_size,
employees, patch_latency, prior_incidents_12m, fin_health, p_true, incident, split`

Key semantics the agent must respect:
- `month` 1–48. `split`: months 1–30 = `train`, 31–48 = `test`.
- `p_true` is the TRUE incident probability (known because the data is
  synthetic). Pages may use it as a reference standard; the models under
  test must never use it as an input.
- `incident` is the observed 0/1 outcome.
- `truth.rds` holds the generating parameters. The TRUE no-SOC-2 effect is
  odds ratio 1.25. The TRUE relationship is confounded: large vendors are
  both more likely to hold SOC 2 AND safer (`beta$size < 0`).

Verified properties of seed 34 (from the committed simulation output):
- Incident rate: 1.45% of vendor-months (209 incidents).
- Naive model (omits `vendor_size`): no-SOC-2 OR 2.04 (95% CI 1.50–2.79).
- Size-adjusted model: OR 1.28 (95% CI 0.89–1.86).
- Median patch latency: 19.9 days (months 1–36) → 26.6 days (37–48),
  reaching 35.0 by month 48. Incident rate rises 1.24% → 2.08%.
- SOC 2 held by 52% of vendors; `cor(vendor_size, soc2_current) > 0.3`.
- IMPORTANT: If any of these numbers differ when you regenerate the data,
  `R/simulate.R` was modified — do not proceed; re-run its test suite and
  report the discrepancy.

## 3. Gate 0 — package check (run before writing any page)

`probcal`, `forecastdom`, and `falsifyr` are brand-new CRAN releases whose
APIs have NOT yet been verified. Before building pages, write and run
`R/check_packages.R`, which for each package: installs it, prints the
version, loads its docs, and runs the ONE function the series needs
against `vendor_panel`:

| Package | Series need | If it fails / API differs, fall back to |
|---|---|---|
| `probcal` | Fit isotonic (main) and Platt calibrators on VendorScore scores; reliability curve data; Brier score; ECE | `probably` (tidymodels); base `isoreg()` |
| `forecastdom` | Diebold–Mariano test with small-sample correction on two monthly forecast-error vectors (months 31–48, n=18) | `forecast::dm.test()` |
| `falsifyr` | Fragility / "smallest kill" analysis on the bank model's `glm` (no-SOC-2 coefficient) | Hand-built: `EValue` + subset-removal robustness loop |

Fallback decision rule: use the CRAN package if it runs and produces the
statistic above; otherwise use the fallback and note the substitution in a
footnote on the relevant page. Do NOT let a broken package block the
series. Record the outcome in `data/package_check.txt` (committed).

## 4. Model construction (`R/fit_models.R`)

### 4.1 VendorScore (the black box)
- Implementation: gradient-boosted classifier (`xgboost` preferred;
  `lightgbm` or `gbm` acceptable). Trained on `split == "train"` (months
  1–30) using `vendor_size, tier, data_access, patch_latency,
  prior_incidents_12m, fin_health, soc2_current` — NOT `p_true`; `incident`
  is the label.
- **Deliberate overconfidence (required):** after fitting, sharpen the
  predicted probabilities on the logit scale:
  `score_adj = plogis(1.5 * qlogis(p_raw))`.
  This pushes probabilities away from 0.5 — high scores become too high,
  low scores too low — producing a classic overconfident (S-shaped)
  reliability curve regardless of library versions. Document it in code
  comments as the planted defect. After generating scores, MEASURE the
  actual calibration defect on the evaluation window (§4.1.1) and describe
  the measured direction in the page text; do not assert it.
- **Black-box discipline:** export ONLY `vendor_id, month, score_adj` to
  `data/vendorscore.parquet` (also CSV if {arrow} is unavailable). Pages 2–3
  consume this file. No page may access the fitted model object, its
  hyperparameters, or its training data — that is the whole point.
- Scores exist for months 1–48 (score all months so the evaluation window
  has scores).

### 4.1.1 Calibration windows (no leakage)
To avoid evaluating a calibrator on the data that fit it, use three
chronological windows for page 2:
- VendorScore training (the vendor's business): months 1–30.
- **Calibrator fitting window: months 1–30.** Fit the isotonic/Platt
  calibrator mapping `score_adj → calibrated score` on these months.
- **Evaluation window: months 31–48.** All reliability diagrams, Brier
  scores, ECE, and tier-movement figures are computed HERE ONLY, on raw and
  calibrated scores. Never report calibrator performance on the fitting
  window.

### 4.2 The bank's own incident-association model (page 4's subject)
- This is NOT an explanation of VendorScore's predictions — it is a
  separate logistic regression the bank built for a different purpose,
  because VendorScore is a black box. Describe it in the pages as "the
  bank's own incident-association model."
- `glm(incident ~ no_soc2 + tier + data_access + log_patch + prior_c +
  fin_health, family = binomial)` fit on the FULL panel. It MUST omit
  `vendor_size` (the planted confounder). Its headline finding — "vendors
  without a current SOC 2 Type II report have ~2× the odds of an incident"
  — drives a contract policy (use beyond intended purpose, §IV).
- Because each vendor appears 48 times, present coefficient uncertainty
  with vendor-clustered standard errors (e.g., `sandwich::vcovCL`) in
  addition to the model-based CIs; note the clustering in one sentence.
- Save the glm and tidy coefficient tables (both SE types) to
  `data/models.rds`.

### 4.3 Naive benchmark forecast (page 3)
- 12-month rolling average of incident counts, computed causally (month t
  uses only months < t). VendorScore portfolio forecast = sum of
  `score_adj` across vendors per month. Actuals = monthly incident totals.

### 4.4 `vendor_summary.md` (what the vendor discloses)
One short fictional markdown doc: vendor name (e.g., "RiskMetric
Systems"), a one-paragraph method description (deliberately vague:
"ensemble machine learning on proprietary threat intelligence"), a claimed
AUC of 0.81 "on vendor development data," and a claim that "scores are
well-calibrated." Pages may quote it; page 2 tests the claim against
NorthPoint's own outcomes.

## 5. Page specifications

Global template for pages 2–4 (follow exactly):
1. The Question (~100 words) — plain-language statement.
2. Method in brief (~200 words) — one main technique; alternatives in a
   single sentence.
3. Findings (~400 words) — figures with full captions; the figure tells
   the story, the text interprets it.
4. So what (~200 words) — consequence for the bank, tied to the guidance.
5. Committee action (~100 words) — one recommendation phrased as "sound
   practice suggests…".

**Do not pre-write conclusions.** The expected findings below are
hypotheses to verify. Compute first, then write text that matches the
measured results — including results that differ from the expectation.

### 5.1 `index.qmd` — Page 1 (~750 words)
- Site/browser title: "Trust, but Verify: Validating a Vendor Risk Model
  You Can't See Inside". H1 on the page: "Three Questions for Any Risk
  Model".
- Sections and budgets: Hook (100w) → The three questions (250w) → The case
  (150w) → The black-box problem, §VII (150w) → How to read this series
  (100w). Total 750.
- Materiality box (inside the three-questions section): rate the vendor
  model on the guidance's §III factors — inherent risk, exposure, purpose
  — in a small aside panel; conclude full validation is warranted.
- One figure: simple three-panel diagram (question → test → decision it
  protects), rendered as SVG; no chart library needed.
- One sentence citing the guidance and where each page fits.

### 5.2 `calibration.qmd` — Page 2 (~1,000 words), package `probcal`
- Question: when VendorScore says 10%, do incidents happen 10% of the time?
- Figure 1 (required): reliability diagram on the evaluation window
  (months 31–48) — binned predicted probability vs observed rate, raw
  scores AND isotonic-calibrated scores, with the aggregate `p_true` rate
  as a reference line.
- Figure 2 (required): bar chart of how many vendors change tier when
  calibrated scores are used, OR a distribution of score movement after
  calibration.
- Table (the one allowed): Brier score, ECE, and expected incident count
  per month — raw vs calibrated, evaluation window only.
- Narrative: describe the measured calibration defect and its direction;
  isotonic recalibration is an overlay/adjustment supported by outcomes
  analysis (§VII, §V) — the bank fixes the scores without touching the
  vendor's code. Contrast with `vendor_summary.md`'s "well-calibrated"
  claim.
- Committee action: sound practice suggests including a reliability
  diagram in every validation pack and setting calibration thresholds that
  trigger recalibration.

### 5.3 `forecast.qmd` — Page 3 (~1,000 words), package `forecastdom`
- Question: does VendorScore beat a 12-month rolling average, and does any
  advantage survive the regime shift?
- Figure 1 (required): monthly actual incident totals vs VendorScore
  portfolio forecast vs naive forecast, months 31–48 (test window), with
  the month-36 regime shift marked by a vertical line.
- Figure 2 (required): cumulative loss differential over the test window
  (where the model gains/loses ground vs naive).
- Table: MSE and MAE per forecast; DM statistic and p-value computed
  (a) over months 31–48, (b) over months 37–48 only. With n=18 the DM
  test has low power — include one sentence that a non-significant result
  means "no detectable advantage," not "proof of equality."
- Write the outcome the data shows. If the pre/post-shift stories differ
  from the hypothesis, the text follows the data.
- One paragraph: the vendor's claimed AUC is on vendor development data;
  it cannot show whether VendorScore stays reliable at THIS bank after
  conditions change — only the bank's own ongoing monitoring can (§VII).
- Committee action: sound practice suggests benchmarking against a named
  simple alternative, out of sample and out of time, and adding the loss
  differential to ongoing monitoring so deterioration triggers review.

### 5.4 `fragility.qmd` — Page 4 (~1,000 words), package `falsifyr`
- Question: how small a change makes the "no SOC 2 → 2× odds" finding
  disappear?
- **Pre-registered definition of "kill" (state it on the page):** the
  smallest perturbation under which the no-SOC-2 coefficient loses
  conventional statistical significance at the 5% level (vendor-clustered
  SEs).
- Figure 1 (required): specification curve — the no-SOC-2 odds ratio
  across reasonable model choices (with/without `vendor_size`,
  with/without prior incidents, with/without `fin_health`, alternative
  link, trimmed outliers), with the TRUE value 1.25 marked as a
  horizontal line.
- Figure 2 (required): the smallest kill under the pre-registered
  definition (hypothesis: adding `vendor_size`, or dropping a handful of
  vendor-months — verify, then report what is actually measured). If
  `falsifyr` is unusable, a hand-built robustness loop.
- Seed-sensitivity paragraph: re-run `R/simulate.R` across seeds 1–40 with
  the FINAL parameters, report the measured range of the naive OR, and
  note in one or two sentences that a finding this sensitive to the random
  seed is itself evidence of fragility.
- Call out §IV Model Use: the bank's incident-association model was built
  for one purpose, then reused to justify a contract policy — use beyond
  intended purpose.
- Series scorecard (closing, ~200 words of the page budget). Fill
  "NorthPoint result" and "Response" from MEASURED findings only:

| Test | Question | NorthPoint result (measured) | Response (guidance language) |
|---|---|---|---|
| Calibration | Honest probabilities? | (from p2) | Overlay: recalibrate output; set thresholds |
| Forecast dominance | Beats a simple model? | (from p3) | Closer monitoring; raise with vendor; ask for development evidence; keep contingency plan |
| Fragility | Robust headline? | (from p4) | Limit use: not a basis for contract policy; document the exception |

Responses use the guidance's own vocabulary: overlay, adjustment,
recalibration, redevelopment, limits on use, documentation (§V, §VI).

## 10. Acceptance criteria (definition of done)

1. `Rscript tests/test_simulate.R` → 34/34 pass (already true; must stay
   true).
2. `Rscript R/fit_models.R` runs clean and produces
   `data/vendorscore.parquet`, `data/models.rds`, `vendor_summary.md`.
3. `quarto render` produces `_site/` with all 4 pages, no errors.
4. Word count script reports total ≤ 4,000 (target ≤ 3,750).
5. Each analysis page: ≤ 3 figures, ≤ 1 table, code folded.
6. Visual QA on every page: no clipped text, no overlapping labels,
   readable axis text, colorblind-safe palette.
7. All reported findings are computed, not assumed: every number on every
   page traces to a cached artifact in `data/`, and the prose matches the
   measured direction of each result.
8. All four pages cite the April 2026 interagency guidance by name and
   date; each page notes that score-based testing is partial validation.
9. `README.md` documents reproduction: `install.R` → `simulate.R` →
   `fit_models.R` → `quarto render`.
10. Nothing in the repo claims the guidance is prescriptive; all committee
    actions read "sound practice suggests…".

## 11. Known risks and mitigations

- New CRAN packages may not work — Gate 0 (§3) handles this; fallbacks
  named; note substitutions in page footnotes.
- OR estimates are seed-sensitive (~200 incidents only). Seed 34 is fixed

  sensitivity across seeds 1–40 with the final parameters.
- DM test with n=18 has low power; report honestly (see §5.3).
- Do not let pages refit models — read cached artifacts only.
